## Chat2Desk daily metrics sync

The backend can import chat-manager response time and ratings from Chat2Desk once per day for the previous day.

Required:

```env
CHAT2DESK_API_TOKEN=your_api_token
```

Optional:

```env
CHAT2DESK_API_BASE_URL=https://api-02.chat2desk.kz
CHAT2DESK_AUTH_SCHEME=raw
CHAT2DESK_SYNC_ENABLED=true
CHAT2DESK_SYNC_TIMEZONE=Asia/Almaty
```

## Контроль опозданий (Workpace)

Раздел «Бот опозданий» следит за отметками сотрудников в Workpace и шлёт нарушения
в рабочие чаты Telegram нашим же ботом. Раньше это был отдельный сервис
`group_late_bot` на Render со своим ботом и состоянием в JSON-файлах — теперь всё
внутри приложения: опрос Workpace раз в 2 минуты идёт джобой планировщика, код
лежит в пакете `group_late/`, а настройки чатов, отбивки, отчёты и журнал опросов —
в таблицах `glb_*`.

Обязательные переменные (без них джоба не заводится, а отчёты собрать нечем):

```env
WORKPACE_LOGIN=your-workpace-login
WORKPACE_PASSWORD=your-workpace-password
```

Необязательные:

```env
WORKPACE_BASE_URL=https://api.workpace.kz
LATE_THRESHOLD_MINUTES=1                    # с какой минуты опоздание — нарушение
GROUP_LATE_MISSING_IN_MINUTES=10            # «отсутствует на месте» после начала смены
GROUP_LATE_MISSING_OUT_MINUTES=60           # «нет отметки об уходе» / «поздний уход»
GROUP_LATE_MAX_REPORT_DAYS=31               # максимальный период одного отчёта
GROUP_LATE_RETENTION_EVENTS_DAYS=180        # сколько хранить отбивки
GROUP_LATE_RETENTION_REPORT_FILES_DAYS=60   # сколько хранить Excel-файлы отчётов
GROUP_LATE_RETENTION_POLL_RUNS_DAYS=7       # сколько хранить журнал опросов
```

Чтобы подключить чат: добавьте бота в группу — она появится в разделе выключенной,
останется включить её тумблером и выбрать отделы.

Вкладка «Сотрудники» показывает дисциплину за период в разрезе отделов Workpace:
ФИО, город, число опозданий и минуты, минуты раннего ухода, неявки и подозрительные
отметки. В таблице **весь состав отдела**, а не только нарушители; нарушения берутся
из `glb_events` по дате смены, поэтому цифры сходятся с «Обзором» и «Отбивками».
Поздний уход и отсутствие отметки об уходе в таблицу не выносятся — они в «Отбивках».

Откуда состав, зависит от того, знаем ли мы отдел у себя. Список пар один на весь
раздел — `GROUP_LATE_BOT_DEPARTMENT_SCOPES` в `bot_schedule2.py` (сейчас
`front_office` → «Регионы»); он же ограничивает раздел главе отдела.

* **Отдел с парой** — состав из iCore: действующие операторы этого отдела
  (`role = 'operator'`, статус не `fired`), с их ФИО и городом. В Workpace числятся
  и другие компании холдинга, поэтому тех, кого нет в iCore, в таблице нет — их
  количество показано подписью под таблицей. Уволенные и руководители попадают в
  таблицу, только если за период у них были нарушения (помечены «вне состава»).
* **Остальные отделы** — состав из кэша `glb_employees`, который наполняет опрос
  Workpace (и кнопка «Обновить из Workpace» на вкладке «Отделы»): сверять не с чем,
  поэтому показываем всех, кого знает Workpace.

Нарушения сшиваются с сотрудником по `employeeId`/`employeeExternalId` и по ФИО.
Связи между справочниками нет, ключ — ФИО, поэтому вне пары матчить нельзя: тёзка
из соседнего отдела подставил бы чужое имя и чужой город. Написание складывается —
казахские буквы к русским, отчество необязательно («ҚҰРМАНОВ ҚАЙРАТ» →
«Курманов Кайрат», «Досанбаев Асан Тестович» → «Досанбаев Асан»), а
фамилия с опечаткой в одну букву при точно совпавшем имени тоже находится
(«УНГАРБАЕВА» → «Сынакабаева»), но только если кандидат в отделе один. Колонка
«Город» появляется только у отделов, где он заполнен.

## Обращения (CRM поверх Telegram-групп)

Раздел «Обращения» убирает ручную переписку операторов в рабочих Telegram-группах.
Оператор проходит готовый сценарий в iCORE, бот относит собранное обращение в нужную
группу, ответы сотрудников возвращаются в ту же карточку, а о выполнении оператор
узнаёт сразу — через колокол уведомлений. Код в пакете `crm/`, данные в таблицах
`crm_*`, эндпоинты на `/api/crm`.

### Сценарии обращений (задача #160)

Ключевое правило ТЗ: **оператор не пишет свободный текст**. Он выбирает тематику,
система задаёт вопросы по одному и не даёт отправить обращение, пока не выполнены
обязательные проверки. Текст для группы собирает сервер, вручную он не редактируется —
специалист получает одинаковую выжимку от всех операторов.

Шесть тематик (`crm/scenarios.py`): пять по Sapar — «Документы не поступили»,
«Не удаётся подписать документы», «Отображается оплата за подписание», «Проверить
статус подписания», «Ошибка в работе Sapar» — и «Уточнение местонахождения посылки».

Что умеет движок сценариев:

* **вопросы по одному**, с возвратом назад и полосой прогресса. Это не украшение:
  в двух тематиках по шестнадцать вопросов, и половина не понадобится, если на
  четвёртом выяснится, что случай не тот;
* **обязательные проверки** перед вопросами, с подтверждением «Проверил — продолжить»;
* **ранний выход**: «документы появились после повторного входа», «ошибка возникла
  один раз», «сервис заработал» — обращение закрывается без сообщения в группу;
* **перевод между тематиками**: документы не отображаются → «Документы не поступили»;
  ошибка на этапе подписания → «Не удаётся подписать документы». Общие ответы
  (ИИН, период, парк) переносятся;
* **валидация**: ИИН ровно 12 цифр, отчётный период месяцем и годом, обязательное
  вложение (скриншот, а для ошибок подписания — скриншот или видео);
* **метка «Возможный массовый сбой»**, если проблема у нескольких водителей;
* **предпросмотр** собранного текста перед отправкой.

Решение о том, можно ли отправлять, принимает **сервер** (`/api/crm/scenarios/<key>/evaluate`).
Интерфейс подсвечивает последствия сразу при ответе, но проверка, которую можно обойти
отключённым JavaScript, проверкой не является — а весь смысл ТЗ именно в том, что без
выполненных проверок обращение в группу не уходит.

Разбивка обращений по тематикам — `/api/crm/reports/scenarios` (отчёт из ТЗ #29).

**Реестр посылок сознательно не подключён.** В исходном ТЗ бот должен был отвечать
автоматически из Google-таблицы, но 11.08.2026 постановщик попросил реестр из проверки
убрать: ссылки закрыты и бот их не читает. Возврат этой проверки — отдельное решение,
сейчас его сторожит тест.

Отдельных переменных окружения раздел не требует: он ходит тем же ботом, что и
остальной портал (`BOT_TOKEN`).

### Что нужно сделать руками один раз

1. **Добавить бота в группу.** Бот запоминает чат сам (обработчик `my_chat_member`,
   общий реестр `it_ticket_channels`), поэтому группа появится в списке без правок кода.
2. **Дать боту право отвечать.** Достаточно обычного участника: штатный privacy mode
   Telegram всё равно отдаёт боту реплаи на его сообщения — именно на них раздел и
   держится.
3. **Привязать группу к очереди** в разделе «Обращения» → вкладка «Очереди» (видна
   глобальному админу). Сами очереди `itaxi_sapar` («iTaxi Sapar») и `parcels`
   («Посылки») создаются при старте автоматически — их не надо заводить руками, иначе
   сценарий не найдёт свой адрес. Остаётся выбрать чат. Одна группа = одна очередь.
   Пока группа не привязана, тематика оператору показывается недоступной.

### Как это работает

* Сообщение в группе несёт номер обращения, тему, описание, приоритет (обычный не
  выделяется никак), клиента и срок ответа, если у очереди задан SLA.
* Кнопок под сообщением нет: «Беру в работу» и «Выполнено» убраны 19.08.2026 —
  из группы они выглядели так, будто ничего не делают. Статус обращения ведут в iCORE.
* Ответ сотрудника **реплаем** на сообщение бота попадает в нить обращения вместе с
  вложениями. Ответ отдельным сообщением в чат до системы не дойдёт — бот его не
  видит, поэтому в каждом обращении стоит прямая просьба ответить реплаем.
* Расписку бот ставит РЕАКЦИЕЙ 👍 на само сообщение сотрудника, а не сообщением в
  чат: подтверждение приходит на каждый принятый ответ и при этом не занимает строку
  в переписке (прежнее «✅ Ответ отправлен оператору по обращению №N» убрано
  25.08.2026). Набор эмодзи у Telegram закрытый — «✅» в реакции не годится.
* Оператор может дописывать в нить из карточки — сообщение уходит реплаем в ту же ветку.
* Если Telegram недоступен, обращение НЕ теряется: остаётся с пометкой «не доставлено»
  и кнопкой «Отправить ещё раз».

### Кому раздел открыт

На время выката раздел видят не все, а отдел СЗоВ, админы и один пилотный оператор.
Границу держат ОБЕ стороны: `crm/access.py::can_open_section` (обязательная, на каждом
эндпоинте) и предикат `canAccessCrmSectionForUser` в `App.jsx` (только про пункт меню).
Список пилотов и код отдела сверяются тестом — иначе пункт был бы виден, а API отдавал 403.

| Кто | Открыт | Периметр обращений |
|---|---|---|
| пилотный оператор (`PILOT_USER_IDS`) | да | только свои |
| остальные операторы и стажёры | нет | — |
| тренер | нет | — |
| супервайзер СЗоВ | да | свои + операторов своих групп |
| супервайзер другого отдела | нет | — |
| глава отдела СЗоВ | да | весь свой отдел и свои очереди |
| глава другого отдела | нет | — |
| глобальный админ | да | всё + настройка очередей и тематик |

Расширить круг — это правка `PILOT_USER_IDS` в `crm/access.py` и `CRM_PILOT_USER_IDS`
в `App.jsx`. Отдельной таблицы под выкат намеренно нет: она переживёт сам выкат.
Удалять обращения может только глобальный админ (ТЗ #29: у оператора «без удаления»).

### Скорость

Замерено на отдельном кластере PostgreSQL с 200 000 обращений и 600 000 сообщений в
нитях (≈2 года работы при 300 обращениях в день) — медиана 7 прогонов EXPLAIN ANALYZE:

| Что | Время | Как читается |
|---|---|---|
| список «мои, в работе» | 0,07 мс | индекс |
| список у админа без фильтров | 0,07 мс | индекс |
| поиск по слову | 0,7–0,9 мс | триграммный индекс |
| поиск по номеру / телефону | 1,4 мс | первичный ключ |
| число непрочитанного | 0,01 мс | index-only |
| запрос колокола | 0,02 мс | частичный индекс |
| карточка + переписка | 0,25 мс | индекс |
| поиск тикета по реплаю (путь бота) | 0,01 мс | индекс |
| создание обращения | 0,31 мс | 7 индексов на запись |
| приём ответа из группы | 0,62 мс | INSERT + UPDATE |

Под одновременной нагрузкой: 16 клиентов × 40 запросов списка — 2000 запросов/с,
медиана 3 мс, 95-й процентиль 11 мс. Приём ответов 12 потоками — 1900/с, медиана 1,2 мс.

Что для этого сделано (каждое — следствие замера, а не догадки):

* **точного «всего N» в списке нет** — ни отдельным `COUNT(*)`, ни `COUNT(*) OVER ()`:
  оба означают полный проход по периметру на каждый фильтр и каждую букву в поиске.
  Вместо него запрашивается одна лишняя строка, и её наличие и есть «показать ещё»;
* **порядок списка — чистые столбцы** `last_message_at DESC, id DESC` под индексом.
  Поэтому `last_message_at` объявлен `NOT NULL`: `COALESCE` в `ORDER BY` отменил бы
  чтение по индексу. «Непрочитанное наверху» отдельным условием не нужно — входящий
  ответ двигает `last_message_at`, и обращение всплывает само;
* **поиск разделён на цифры и слова.** Одно ИЛИ на пять условий планировщик
  обслуживать индексами отказывался: редкое слово искалось 270 мс, отсутствующее —
  187 мс, а частое находилось за 0,6 мс просто потому, что совпадения попадались в
  первых строках. Разделённые ветки укладываются в 1,7 мс;
* **триграммный индекс по столбцам, а не по выражению.** С `COALESCE(client_name,'')`
  в индексе запрос по самому столбцу его не видел — 124 мс проходом по таблице;
* **числа шапки сведены к одному** и считаются один раз при открытии раздела.
  Из шести агрегатов четыре интерфейс не показывал вовсе, а «сколько всего с ответом»
  стоило 13 мс на 33 тыс. записей ради подписи сегмента;
* **история действий грузится по кнопке**, а не с каждой карточкой;
* **нить ограничена 300 последними сообщениями** — на случай, если группа уйдёт
  в обсуждение;
* **раздел не открывает своего SSE-канала** и не опрашивает сервер по таймеру. Он
  реагирует на изменение отпечатка своего источника в сводке колокола: широковещательный
  тычок (новый пост «Ивентов» будит все вкладки) раздел не трогает.

### Реалтайм

Своего SSE-канала раздел не открывает. «Тычок» о том, что у пользователя что-то
изменилось, уже приходит колоколу (`/api/notifications/stream`); колокол отдаёт наружу
отпечаток состава сводки по источникам (`onDigest`), и раздел перечитывает данные
ровно тогда, когда изменился ЕГО отпечаток. Триггер `trg_bell_crm_tickets` будит
только автора обращения и только когда изменилось непрочитанное, статус или доставка:
исходящее сообщение в нить сводку не меняет и тычка не стоит.

## Касания (звонки отдела продаж из CDR АТС)

Раздел показывает и выгружает касания — звонки клиентам с АТС FreePBX отдела
продаж, склеенные из строк CDR по `linkedid`.

**Портал к станции не ходит.** Станция стоит в корпоративной сети; 25.08.2026 её
выводили наружу через прокси с basic-auth — в тот же день сервис лёг, и доступ
закрыли. Данные приносит мост из корпоративной сети: `cdr_bridge/` (установка и
эксплуатация — `cdr_bridge/README.md`). Мост делает только исходящие запросы, ни
одного порта наружу не открывается.

На стороне портала нужна одна переменная:

```env
CDR_AGENT_TOKEN=            # общий с мостом токен, ТОЛЬКО ASCII
```

Токен генерируется `python -c "import secrets; print(secrets.token_urlsafe(32))"`
и прописывается одинаково на Render и на VM с мостом. Только ASCII: HTTP-заголовок
ходит в latin-1, и токен с кириллицей не отправится вовсе.

Пока переменная не задана, ручки моста отвечают 503 (а не пускают кого попало), а
раздел работает на том, что уже лежит в базе, и честно пишет, что мост не на связи.

Кому открыт: глобальные админы, глава отдела продаж и супервайзеры ОП. Оператору
и тренеру — нет: выгрузка это телефоны клиентов за период целиком.

## Лиды OLX (робот переноса откликов в amoCRM)

Задача #223. Робот следит за чатами девяти кабинетов OLX и заводит по каждому
новому обращению сделку в amoCRM: воронка «Отдел продаж», этап «Новая заявка»,
название сделки — телефон в формате `77XXXXXXXXX`, тег кабинета, ответственный
«Администратор», контакт с тем же номером в поле «Раб. тел.». Если номера в
обращении нет, кандидату уходит заготовленный ответ с телефоном того кабинета,
куда он написал.

Опрос идёт **дважды в минуту** (`CronTrigger(second='0,30')`), кабинеты
обходятся параллельно на своём пуле потоков. Накопительная выгрузка раз в час
требованию постановки не соответствует — это записано в ТЗ отдельным пунктом.

Раздел «Лиды OLX» показывает журнал обращений, сводку за день и состояние
кабинетов. Открыт глобальным админам и главам «Маркетинга» и отдела продаж;
подключать кабинеты может только глобальный админ.

### Что нужно получить от OLX (без этого робот не поедет)

Чаты Partner API отдаёт **только в пользовательском контексте**: `client_credentials`
даёт справочники и на `/threads` получает 401. Значит на каждый кабинет нужны

```env
OLX_CLIENT_ID_1..9=         # id приложения, выданный OLX
OLX_CLIENT_SECRET_1..9=     # секрет приложения; если не задан, берётся OLX_API_KEY_N
OLX_REDIRECT_URI=           # адрес возврата, ВПИСАННЫЙ В ЗАЯВКУ на приложение
```

`OLX_REDIRECT_URI` обязан совпадать с тем, что указано в заявке OLX, иначе обмен
кода на токены будет отвергнут. Он один на все девять приложений, поэтому живёт
в окружении, а не вводится руками девять раз. Рабочее значение:

```
https://otp-2-fos4.onrender.com/api/olx_amo/oauth/callback
```

Это страница, которая показывает код согласия и ничего с ним не делает. Она
намеренно БЕЗ авторизации: на неё приходит редирект браузера от OLX, а заголовка
с токеном портала в нём нет. Обменивай она код сразу — любой, кто открыл ссылку,
подключал бы кабинеты к нашей CRM без единой проверки прав; поэтому «показать
код» и «применить код» разведены, и второе делается уже из раздела, под админом.

Если в заявке какого-то кабинета стоит голый адрес сервиса
(`https://otp-2-fos4.onrender.com`), перезаводить заявку не обязательно: браузер
уедет на страницу «Bot is alive!», а код останется в адресной строке — скопируйте
адрес целиком и вставьте в поле, нужное раздел достанет сам.

**Менять уже вписанный в заявку адрес не нужно.** Если тем же приложением
пользуется что-то ещё, подмена сломает ЕГО экран согласия (на выданные токены и
на вызовы API адрес не влияет — только на согласие). Подстраиваемся мы:

```env
OLX_REDIRECT_URI_4=         # свой адрес для кабинета №4, главнее общего
```

Порядок такой: явный параметр запроса → `OLX_REDIRECT_URI_<N>` → общий
`OLX_REDIRECT_URI`. Заполнять по кабинетам нужно только там, где в заявке стоит
адрес, отличный от общего.

Присланные в файле доступов `OLX_API_KEY_1..5` — это половина пары. Второй
половины (`client_id`) в выгрузке нет, а id кабинета (`62369008` и прочие)
client_id **не является**: токен-ручка отвечает на него `Client is not active`.
Тот же ответ приходит и на заведомо выдуманный id — OLX склеивает «приложение не
найдено» и «приложение не одобрено» в одну ошибку, поэтому отличить их можно
только в кабинете разработчика на developer.olx.kz.

Приложение заводится на **developer.olx.kz** (не на apps.olxgroup.com — это
другой продукт OLX Group с другим хостом и другими скоупами) и проходит ручную
модерацию: до одобрения оно висит в статусе «Waiting for acceptance».

### Как подключить кабинет после получения доступов

1. Прописать `OLX_CLIENT_ID_N` (и при необходимости `OLX_CLIENT_SECRET_N`) в
   переменных окружения Render.
2. `GET /api/olx_amo/cabinets/<код>/authorize?redirect_uri=<адрес из заявки>` —
   раздел вернёт ссылку на экран согласия.
3. Открыть ссылку **в браузере, где выполнен вход именно в этот кабинет OLX**.
   Согласие выдаёт тот, кто вошёл, а не тот, чей client_id в ссылке; перепутать
   вход — самая частая ошибка подключения: токен приедет, но чужой.
4. Скопировать `code` из адресной строки и отдать его
   `POST /api/olx_amo/cabinets/<код>/callback` телом `{"code": "...", "redirect_uri": "..."}`.
   Код живёт считанные секунды.

Дальше робот живёт сам: `refresh_token` хранится в базе и обновляется. OLX
**ротирует** его при каждом обновлении, поэтому токены пишутся парой и одной
транзакцией — потерянный refresh означает повторное согласие владельца кабинета.

### Предохранитель первого запуска

В девяти кабинетах лежат накопленные непрочитанные чаты за месяцы. Без
ограничения первый же опрос завёл бы сделку по каждому — задним числом, поверх
той работы, что маркетолог уже сделал руками. Дедупликация тут не помогает: она
работает в границах суток, а история лежит по разным дням.

Поэтому у чата, который робот видит впервые, разбираются только сообщения не
старше горизонта:

```env
OLX_MESSAGE_HORIZON_HOURS=6   # по умолчанию 6 часов
```

**На первом боевом запуске поставьте его в доли часа**, посмотрите журнал
раздела и только потом отпускайте. Уже отслеженные чаты горизонт не трогает — у
них своя закладка, и она точнее.

### Уведомления и выгрузка

Раздел 7 ТЗ требует сообщать ответственным о простое, потере авторизации,
ошибках передачи в amoCRM и подозрительной тишине по кабинету.

**Куда слать — выбирается в самом разделе**, блок «Уведомления о сбоях»: список
показывает группы, в которые уже добавлен бот, и админ отмечает нужные. Свой
реестр групп раздел не заводит — те, куда бота добавили, копятся в общей таблице
портала (её наполняет обработчик `my_chat_member`), из неё же берут списки
«Обращения» и «Бот опозданий». Переменной окружения здесь нет намеренно: состав
адресатов меняют живые люди чаще, чем выкатывается релиз.

Пороги при этом настраиваются окружением:

```env
OLX_IDLE_ALERT_MINUTES=15   # простой, после которого это авария
OLX_SILENCE_ALERT_HOURS=12  # тишина по кабинету, после которой это подозрительно
```

Проверка идёт каждые 5 минут, но **сообщение уходит только на смене состояния**:
одно и то же каждые пять минут перестают читать через час, и настоящая авария
теряется среди повторов. О восстановлении сообщается тоже. Пока не выбрана ни
одна группа, уведомления не рассылаются, а состояние всё равно видно в разделе.

Журнал выгружается кнопкой «Выгрузить» за тот период и кабинет, что выбраны на
экране (`GET /api/olx_amo/journal/export`) — .xlsx с обеими формами номера,
временем отклика и временем сделки, тегом, исходом и текстом обращения.

### Что робот берёт в разбор

Непрочитанного мало: чат, который маркетолог открыл в кабинете раньше робота,
теряет счётчик непрочитанного, и по нему одному робот к чату уже не подойдёт.
Так 02.09.2026 потерялись четыре обращения, два из них с телефоном. Поэтому
кандидатов три вида:

* есть непрочитанное — обычный случай;
* чат уже знаком, и **общее число сообщений** в нём выросло — значит появилось
  новое, даже если непрочитанное погашено человеком. Считаем именно общее:
  оно только растёт, а непрочитанное гасится и возвращается к прежнему значению;
* чат совсем новый и создан не раньше горизонта — его мог открыть человек в те
  секунды, что прошли до опроса.

Сообщения дочитываются только у отобранных, поэтому расход запросов почти не
растёт: список чатов и так приходит целиком.

### Что видит кандидат

Робот пишет кандидату РОВНО ОДИН раз за обращение и только в одном случае —
когда в сообщении нет телефона. Всё остальное происходит молча:

| Что сделал кандидат | Что делает робот | Что кандидат видит |
|---|---|---|
| Прислал отклик с телефоном | заводит сделку | ничего |
| Написал без телефона | заготовленный ответ с номером кабинета | ответ |
| Написал ещё раз после автоответа | помечает чат «ждёт ответа человека» | ничего |
| Тот же номер второй раз за день, тот же кабинет | ничего, в журнале «повтор» | ничего |
| Тот же номер в другом кабинете | заводит вторую сделку | ничего |
| Номер иностранный или с опечаткой | сделка с пометкой «нужна проверка» | ничего |

Второго автоматического сообщения нет намеренно — решение владельца
02.09.2026: оно раздражает и читается как поломка. Вместо него чат всплывает
в разделе блоком «Ждут вашего ответа» со ссылкой прямо на переписку, и
маркетолог отвечает сам. Метка снимается автоматически, как только в чате
появляется наше исходящее сообщение.

### Ответ кандидату из раздела

Вкладка «Диалоги» — двухпанельный экран, как в «Обращениях»: слева чаты
(ждущие ответа сверху), справа переписка и поле ввода. Сотрудник отвечает, не
уходя в кабинет OLX; сообщение уходит в тот же чат от имени компании.

Что при этом происходит на сервере, и почему именно так:

* **Строка отправки заводится ДО похода в сеть**, со статусом `pending`. У
  автоответа робота порядок обратный — там страшнее разослать копии, — а здесь
  страшнее потерять текст, который человек уже написал. Не доехавший ответ
  остаётся в переписке помеченным «не отправлено», а не исчезает.
* **Двойное нажатие не отправит дважды.** Ключа идемпотентности у ручки OLX нет,
  поэтому замок свой: тот же текст в тот же чат за 15 секунд отвергается.
* **Роботу закрывается рот.** В той же транзакции снимается метка ожидания и
  ставится отметка автоответа, иначе робот, начавший цикл секундой раньше,
  положил бы своё «позвоните по номеру» поверх живого ответа.
* **Авторство хранится у нас.** OLX помечает сообщение только направлением, и
  робот, ответ из раздела и написанное руками прямо в кабинете там неразличимы.
  Поэтому исходящие пишутся в `olx_outbound` с автором, а сообщение без нашей
  строки подписывается «Из кабинета OLX» — врать «Робот» нельзя.
* **Неудача видна сразу**: 409 — кабинет отключился, 429 — лимит OLX с временем
  ожидания, 400 — пустой или слишком длинный текст, 502 — прочее. Молчаливого
  «ок» при недоставленном сообщении нет.

Отвечать может тот же, кто видит раздел (`can_reply` в `olx_amo/access.py`).
Вынесено отдельной способностью намеренно: это единственное действие раздела
наружу, и когда периметр придётся расширить, менять надо будет одно место.

### Что видно в самой переписке

Кроме реплик, в ленте стоят системные отметки — по центру и мельче сообщений,
как пометки на полях: «Создана сделка» со ссылкой на неё и временем доставки,
«Повтор за сутки — сделку не заводили», «Номер требует проверки», «Ждёт ответа
человека», «Не доехало в amoCRM» с текстом ошибки.

Без них диалог выглядел бы разговором без последствий: кандидат написал,
сотрудник прочитал — а завелась ли сделка, видно только в amoCRM. Отметки
отвечают на это прямо здесь.

Автоответ робота и ответ сотрудника отметками НЕ дублируются: сами эти
сообщения уже стоят в ленте пузырями, и подпись «отправлен ответ» рядом с ним
была бы той же информацией дважды.

### Защита от дублей и от тихого простоя

Дедупликация — частичный уникальный индекс по (кабинет, нормализованный номер,
дата) в `olx_journal`. Проверка в коде идёт первой, но полагаться на неё нельзя:
девять кабинетов опрашиваются параллельно, и гонку ловит только база.

Отметка об опросе (`olx_accounts.last_poll_at`) ставится **на каждом опросе,
включая пустой** — иначе «обращений нет» неотличимо от «робот перестал видеть
чаты». Раздел подсвечивает кабинеты, молчащие дольше 15 минут (порог из ТЗ).

Ошибка передачи в amoCRM не теряет обращение: строка журнала с `result='error'`
и есть очередь на повтор, её раз в пять минут разбирает `olx_amo_retry`.

## Вики: база знаний Яндекс Про

Статья вики может быть подписана на страницу `pro.yandex.com/.../knowledge-base/...`.
Импорт разбирает страницу целиком (текст свёрнутых блоков в отрендеренном HTML
отсутствует — читается состояние Next.js), переносит картинки в наш бакет с
переводом в WebP и оставляет статью связанной с источником.

Раз в сутки джоба `wiki_yandex_pro_sync_daily` сверяет отпечаток содержимого
страницы. Изменился — статья обновляется, редакция уходит в историю версий.
Если статью с прошлой сверки правили руками, автоматика **ничего не
перезаписывает**: страница помечается конфликтом и ждёт кнопки «Обновить из
источника». Ключ сопоставления — канонический адрес страницы, поэтому повторный
импорт не плодит статьи.

Переменные необязательные, всё работает и без них:

```env
WIKI_YANDEX_PRO_SYNC=1          # 0 — не ходить наружу вовсе (прод без интернета)
WIKI_YANDEX_PRO_SYNC_HOUR=5     # час ночной сверки по Алматы
WIKI_YANDEX_PRO_SYNC_MINUTE=0   # минута ночной сверки
```

Пока ни одна статья не связана с источником, прогон не делает ни одного запроса
наружу.

## GitHub Pages

1. Push repository to GitHub (branch `main` or `master`).
2. Open repository settings: `Settings -> Pages`.
3. In **Build and deployment**, choose **Source: GitHub Actions**.
4. Workflow `.github/workflows/deploy-pages.yml` will build and publish automatically.
5. Wait for workflow completion in `Actions` tab and open published URL.

### Base path notes

- For GitHub Pages we use `VITE_BASE_PATH=/${REPO_NAME}/` in workflow.
- For custom domain (root), use `/` as base path.

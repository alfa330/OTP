# Контракт TEZ APP: даты заказов водителя

Статус: **закрыт 11.08.2026.** Запрашивали поле «последний заказ водителя» под
правило успешки за реактивацию — TEZ APP его добавил. Ниже зафиксировано, что
эндпоинт отдаёт на самом деле (проверено на боевых номерах), потому что от этих
дат напрямую зависит выплата операторам отдела продаж.

## Что отдаёт эндпоинт сейчас

```
POST https://api.tezapp.org/drivers/first-orders
X-Integration-Token: <prod-токен>

{"month": "2026-08", "drivers": [{"full_name": "...", "phone": "+77012345678"}]}
```

```json
{
  "drivers": [
    {
      "full_name": "...",
      "phone": "+77012345678",
      "month_first_order_at": "2026-08-08T09:52:05.136058+05:00",
      "last_order_before_at": "2026-06-19T10:20:27.24335+05:00"
    }
  ]
}
```

| поле | смысл |
|---|---|
| `month_first_order_at` | первый заказ в запрошенном месяце, `null` — заказов в нём нет |
| `last_order_before_at` | последний завершённый заказ строго **до 1-го числа запрошенного месяца**, за всё время. `null` — заказов не было вообще |

Семантика `last_order_before_at` проверена сравнением двух запросов по одному
водителю: `month=2026-07` отдаёт последний заказ 30 июня, `month=2026-08` по
тому же водителю — последний заказ июля. То есть граница привязана к началу
запрошенного месяца, а не к дате первого заказа в нём, и значение для пары
(водитель, месяц) не меняется — поэтому мы спрашиваем его один раз и кэшируем.

Разрыв простоя считаем у себя: `month_first_order_at − last_order_before_at`.

## Ломающее изменение, которое приехало вместе с этим

Поле **`previous_month_first_order_at` из ответа убрано.** Наш код читал его как
`null`, и правило «водитель уже работал в прошлом месяце» молча перестало
срабатывать. Лишних успешек это не начислило (проверено: все августовские
успешки проходят и по новому правилу, разрывы 73–125 дней), но защиты не было.

Что сделано у нас: правило переведено на `last_order_before_at`, сохранённые
даты закрытых периодов больше не перетираются ответом API, а пропажа
`last_order_before_at` из ответа теперь пишется в лог — молча деградировать до
«успешек нет» это правило больше не может.

**Просьба на будущее:** предупреждать об удалении полей заранее. Пропажа поля не
даёт ни ошибки, ни пустого ответа — она тихо меняет то, сколько денег получит
оператор.

## Что осталось уточнить

**Что считается заказом — только завершённая поездка?** Мы исходим из того, что
да. Это важно: одна отменённая поездка в середине простоя обнулит разрыв в
30 дней и снимет с оператора уже заслуженную успешку.

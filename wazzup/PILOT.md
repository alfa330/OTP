# Пилот обработки чатов для alfa330

Раздел «Чаты ОП → Верификаторы», аккаунт `op`. Отправка текста и SSE доступны
только пользователю с логином `alfa330`, который уже имеет доступ
к разделу. Ограничение повторяется на сервере для каждого метода; остальные
пользователи продолжают пользоваться архивом. Отправка в два известных канала
Global запрещена сервером. Архив Global остаётся доступен для просмотра.
Статусы учётной записи `fired`/`dismissal` закрывают доступ. Признак
`users.is_active` обозначает работу оператора на линии и не ограничивает админа.

## Запуск

Нужен обычный деплой backend и frontend из одного изменения. При старте
`Database._init_db` создаёт таблицы, функции и триггеры из `pilot_schema.py`.
Дополнительных секретов нет: отправка использует существующий `WAZZUP_OP_API_KEY`,
слушатель PostgreSQL — обычные `POSTGRES_*` приложения. Ключ в браузер не передаётся.
Вебхук Wazzup должен, как и прежде, присылать входящие, исходящие и статусы.

После деплоя: войти как alfa330, открыть «Чаты ОП → Верификаторы», выбрать
активный личный WhatsApp-чат вне Global. Над списком появится состояние связи,
под перепиской — поле ответа. Enter отправляет, Shift+Enter добавляет строку. Первое сообщение
следует проверять с согласованным тестовым получателем; автоматические проверки
этого изменения клиентам ничего не отправляют.

Успех POST означает принятие Wazzup. «Отправлено», «Доставлено», «Прочитано»
появляются по вебхуку. Это статусы прочтения клиентом исходящего сообщения;
открытие входящего чата не отправляет команду «прочитано» в WhatsApp.

## Доставка и восстановление

- Один PG LISTEN на процесс, затем рассылка по SSE. Нет запросов к базе на
  каждый heartbeat. События PostgreSQL видны только после COMMIT.
- Максимум 8 потоков пилота на процесс; каждый занимает поток Waitress.
  Скрытая вкладка закрывает SSE. Переавторизация каждые 120–140 секунд,
  повторное соединение с задержкой, heartbeat 20 секунд, watchdog 65–75 секунд.
- Статусы применяются прямо из SSE без SELECT и повторного HTTP чтения переписки.
  Новые/изменённые сообщения слушатель загружает вместе со сводкой чата одним
  запросом на пакет до 100 сообщений, независимо от числа подписчиков.
  На каждого клиента запросов нет. Если подписчиков нет, загрузка не выполняется.
  Буфер ограничен 2048 событиями/8 MiB; редкие события больше 256 KiB восстанавливаются
  через HTTP. Только при отсутствии данных события действует задержка восстановления
  переписки 350 мс и списка 1 секунда.
  После переподключения перечитывается отображаемый диапазон истории;
  ответ ограничен 2000 сообщениями, при переполнении остаются последние 2000.
  Ошибки чтения повторяются с паузой, без непрерывного опроса.
- Исходящая попытка фиксируется в outbox до HTTP-запроса. Повтор того же UUID
  не отправляет ещё одно сообщение, включая таймаут и перезапуск приложения.
  Wazzup сам проверяет `crmMessageId` лишь в течение 60 секунд:
  [документация v3](https://wazzup24.com/help/api-en/sending-messages/).
- После неопределённого результата черновик блокируется. «Проверить отправку»
  проверяет прежнюю попытку. Для нового сообщения нужно явно подтвердить
  проверку переписки. Черновик и UUID сохраняются в sessionStorage этой вкладки.
- Ранние статусы ждут сообщения в отдельной таблице до двух суток;
  delivered/read не откатываются поздними sent/error. История остаётся 45 дней.
  Текст outbox очищается по тому же сроку, UUID остаются для защиты от дублей.

Пилот включает текстовые ответы, входящие/исходящие сообщения, изменения,
удаления и статусы из вебхуков. Вложения доступны для просмотра существующим
интерфейсом. Отправка файлов, назначение/блокировка чата оператору и аккаунт
«Поток» в этот пилот не входят.

## Шаблоны, эмодзи и непрочитанные

`/` в начале ответа или `+ Шаблоны` открывает поиск. Одобренные текстовые WABA
шаблоны загружаются через `GET /v3/templates/whatsapp` и отбираются по каналу.
Кеш на процесс — 10 минут, при сбое копия не старше часа с предупреждением.
Переменные заполняются до вставки; оператор видит текст, а Wazzup получает
документированный `@template:` код. Проверка канала/переменных выполняется сервером
до создания outbox. Код остаётся частью неизменяемой попытки отправки.

Текущий API-ключ даёт WABA (на проверке 63 шаблона). Обычные быстрые шаблоны
Wazzup через `/v2/templates/wz` требуют отдельного партнёрского `client_access_token`:
они пока не импортируются. Это ограничение отражено в интерфейсе. Источники:
[WABA](https://wazzup24.com/help/api-en/whatsapp-business-api-templates/),
[обычные шаблоны](https://wazzup24.ru/help/api/templates-wz/).

`+ iCORE` создаёт общий текстовый шаблон в `wazzup_quick_templates` (до 250).
Собственные шаблоны можно изменять и удалять; в Wazzup они не публикуются.
Эмодзи — Unicode с поиском на русском, категориями и оттенками кожи.
Каталог загружается отдельным файлом только при открытии; вид символов зависит от ОС.

Общий счётчик означает «Ожидают ответа». Открытие и прокрутка чата его не снимают.
Ответ оператора через Wazzup/iCORE закрывает входящие, отправленные до ответа;
кнопка «Ответ не нужен» явно закрывает текущую очередь. Условная запись по
последнему входящему messageId защищает новое входящее от случайного сброса.
Изменения передаются команде через SSE. Global и «Поток» исключены.

`wazzup_chat_read_state` хранит счётчик и время последнего ответа;
`wazzup_unanswered_messages` — только ID/время ожидающих входящих. Повтор webhook,
редактирование, статусы доставки и анонимное приветствие интеграции не добавляют
новых входящих. Ответ определяется по authorName/authorId, sentFromApp или outbox
iCORE; для анонимной сторонней интеграции webhook не позволяет отличить бота от
человека. Ошибка отправки не закрывает очередь; поздний ответ не закрывает более
новые входящие. Миграция один раз пересчитывает только уже отслеживаемые чаты,
сохраняя ручные нули; весь архив непрочитанным не становится.

«Ответ не нужен» — общее состояние iCORE, не команда прочтения WhatsApp и не
синхронизация ручной отметки в Wazzup. Публичный API возвращает общий счётчик
пользователя, но не предоставляет документированного сброса отдельного чата:
[счётчики Wazzup](https://wazzup24.com/help/api-en/unanswered-counter/).

## Ответы и редактирование черновика

Стрелка у сообщения выбирает цитату. Отправка использует документированный
`refMessageId`; сервер проверяет принадлежность исходного сообщения чату.
Цель ответа сохраняется в outbox и входит в проверку повторного UUID.
Собственные цитаты видны в истории/refresh/SSE, даже если оригинал не загружен
в текущую страницу; удалённый текст оригинала не возвращается.

Кнопки RU/ҚАЗ и перефраз меняют только черновик. Используется существующий
Vertex-провайдер приложения, модель `WAZZUP_DRAFT_AI_MODEL` (по умолчанию
`gemini-3-flash-preview`). В ИИ передаётся только выбранный черновик, не история.
Два параллельных запроса на процесс и 12 запросов на пользователя в минуту;
HTTP-таймаут провайдера 12 секунд, клиентский 25 секунд. Результат можно отменить;
изменение текста или переход в другой чат отменяет применение старого результата.
Числа, ссылки и email проверяются до замены. Одобренные WABA-шаблоны не редактируются.

Поле ввода начинается с одной строки и растёт до 160 px. Кнопка шаблонов — `/`.
Текст сообщений 16 px, переписка и ввод ограничены 900 px на широких экранах.
Дата первого видимого сообщения появляется при прокрутке и исчезает через 900 мс;
поиск видимого сообщения не сканирует всю ленту, скролл тонкий.

WABA-шаблон передаётся как `@template:` и может тарифицироваться. Wazzup указывает,
что текстовый шаблон внутри активного 24-часового окна может быть отправлен как
обычное сообщение; с октября 2026 для сервисных сообщений действует лимит
1000 бесплатных на номер в месяц. Итог зависит от типа, страны и условий Wazzup:
[тарификация](https://wazzup24.ru/help/payment/whatsapp-business-api-charging/),
[изменения октября](https://wazzup24.com/help/waba/updates-october-2026/).
Обычные быстрые ответы ещё не перенесены: браузер этой сессии недоступен.

Проверка этой версии: 203 Python-теста (22 subtests), 62 JavaScript-теста,
production-сборка Vite. Реальные вызовы ИИ на трёх вымышленных черновиках:
перефраз 3.61 с, перевод на казахский 1.58 с, на русский 1.65 с.
Read-only предварительный расчёт на рабочей БД: 86 чатов/422 входящих →
7 чатов/10 входящих, ручные нули сохранены. Это снимок до выкладки, не счётчик
на текущий момент. Визуальная проверка и отправка цитаты реальному получателю
ещё не выполнялись; автоматические проверки не отправляли WhatsApp-сообщений.

## Проверка оптимизации 06.10.2026

170 Python-тестов и 51 JavaScript-тест прошли; production-сборка успешна.
Проверены реальные SQL/триггеры, конкурентная отметка прочтения, дубли webhook,
пагинация, ограничения доступа, отложенные ответы HTTP/SSE, шаблоны и эмодзи.
Браузер для визуальной проверки в этой сессии недоступен.

`python scripts/benchmark_wazzup_pilot_hydrated.py --port 15436` на изолированном
локальном PostgreSQL: 6 SSE и 24 фоновых потока, 300 событий по 30/сек,
1800/1800 доставок. На 100 событий содержимого выполнено всего 100 SELECT;
на 200 статусов — 0. PostgreSQL hydrate → HTTP SSE: p50 3.11 мс, p95 14.96 мс,
p99 17.84 мс; обычный HTTP GET p95 13.43 мс. Это локальный замер без Wazzup,
webhook/NOTIFY, прокси, production-авторизации и отрисовки браузера.

## Проверки 06.10.2026

`tests/test_wazzup_pilot.py` — ограничения доступа, защита повторов, таймаут,
конкурентные отправки, изоляция чтения, восстановление истории и ограничения SSE.
`tests/test_wazzup_pilot_persistence.py` выполняет настоящие SQL на отдельном
локальном PostgreSQL (`WAZZUP_PILOT_TEST_PORT`), включая конкурентные статусы/эхо.
Не запускает приложение и не подключается к production.

`tests/wazzup_chat_pilot.test.mjs` и `tests/wazzup_pilot_realtime.test.mjs` проверяют
черновики, двойной клик, неопределённую отправку, объединение событий,
закрытие/восстановление потоков, watchdog и задержку повторов при ошибке базы.
Итого прошли 123 Python-теста (включая 12 на локальном PostgreSQL),
44 JavaScript-теста и production-сборка Vite. Визуальная проверка в браузере
и отправка реальному получателю не выполнялись.

Локальный транспортный benchmark:

```powershell
python scripts/benchmark_wazzup_pilot.py --clients 6 --events 300 --rate 30 --background-streams 24
```

Waitress 96 потоков, 6 SSE пилота плюс 24 фоновых потока: 1800/1800 доставок,
publish→SSE p95 3.98 мс, максимум 10.09 мс. Обычный HTTP GET p95 6.43 мс,
ошибок и утечек слотов нет. Это локальный транспорт, без Wazzup, PostgreSQL,
прокси, браузерного обновления и production-авторизации.

Малый read-only замер текущей БД (`scripts/benchmark_wazzup_pilot_db.py --run`):
6 имитированных клиентов, 3 цикла, 72 SELECT через 2 соединения служебной роли.
У этой роли лимит 2; это не пул приложения (по умолчанию 16–40).
С учётом сети от рабочей станции p95: COUNT чатов 98.65 мс, список 112.11 мс,
сообщения LIMIT 50 — 92.82 мс, LIMIT 200 — 195.46 мс.
Выбранный чат содержал лишь 17 сообщений: этот тест не характеризует длинные
переписки. Очередь на два соединения достигала 3.83 с, цикл с очередью — 4.45 с.
Она не является измерением задержки рабочего интерфейса.

Результаты подтверждают работоспособность транспорта для 6 подключений.
Полную задержку Wazzup→вебхук→браузер, длинные истории и одновременную нагрузку
остальных разделов следует измерять на сервере после выкладки. Общие лимиты
SSE колокола/аукциона и пилота пока независимы; перед массовым включением
следует проверить суммарное число занятых потоков Waitress.

# Пилот обработки чатов для alfa330

Раздел «Чаты ОП → Верификаторы», аккаунт `op`. Отправка текста и SSE доступны
только активному пользователю с логином `alfa330`, который уже имеет доступ
к разделу. Ограничение повторяется на сервере для каждого метода; остальные
пользователи продолжают пользоваться архивом. Отправка в два известных канала
Global запрещена сервером. Архив Global остаётся доступен для просмотра.

## Запуск

Нужен обычный деплой backend и frontend из одного изменения. При старте
`Database._init_db` создаёт таблицы, функции и триггеры из `pilot_schema.py`.
Дополнительных секретов нет: отправка использует существующий `WAZZUP_OP_API_KEY`,
слушатель PostgreSQL — обычные `POSTGRES_*` приложения. Ключ в браузер не передаётся.
Вебхук Wazzup должен, как и прежде, присылать входящие, исходящие и статусы.

После деплоя: войти как alfa330, открыть «Чаты ОП → Верификаторы», выбрать
активный личный WhatsApp-чат вне Global. Над списком появится состояние связи,
под перепиской — поле ответа. Отправка кнопкой или Ctrl+Enter. Первое сообщение
следует проверять с согласованным тестовым получателем; автоматические проверки
этого изменения клиентам ничего не отправляют.

Успех POST означает принятие Wazzup. «Отправлено», «Доставлено», «Прочитано»
появляются по вебхуку. Это статусы прочтения клиентом исходящего сообщения;
открытие входящего чата не отправляет команду «прочитано» в WhatsApp.

## Доставка и восстановление

- Один PG LISTEN на процесс, затем рассылка по SSE. Нет запросов к базе на
  каждый heartbeat. События PostgreSQL видны только после COMMIT.
- Максимум 8 потоков пилота на процесс; каждый занимает поток Waitress.
  Скрытая вкладка закрывает SSE. Переавторизация каждые 120–140 секунд,
  повторное соединение с задержкой, heartbeat 20 секунд, watchdog 65–75 секунд.
- Интерфейс объединяет события: обновление открытой переписки через 350 мс,
  списка — максимум раз в секунду. Статус без изменения текста не обновляет список.
  После переподключения перечитывается отображаемый диапазон истории;
  ответ ограничен 2000 сообщениями, при переполнении остаются последние 2000.
  Ошибки чтения повторяются с паузой, без непрерывного опроса.
- Исходящая попытка фиксируется в outbox до HTTP-запроса. Повтор того же UUID
  не отправляет ещё одно сообщение, включая таймаут и перезапуск приложения.
  Wazzup сам проверяет `crmMessageId` лишь в течение 60 секунд:
  [документация v3](https://wazzup24.com/help/api-en/sending-messages/).
- После неопределённого результата черновик блокируется. «Проверить отправку»
  проверяет прежнюю попытку. Для нового сообщения нужно явно подтвердить
  проверку переписки. Черновик и UUID сохраняются в sessionStorage этой вкладки.
- Ранние статусы ждут сообщения в отдельной таблице до двух суток;
  delivered/read не откатываются поздними sent/error. История остаётся 45 дней.
  Текст outbox очищается по тому же сроку, UUID остаются для защиты от дублей.

Пилот включает текстовые ответы, входящие/исходящие сообщения, изменения,
удаления и статусы из вебхуков. Вложения доступны для просмотра существующим
интерфейсом. Отправка файлов, WABA-шаблоны, назначение/блокировка чата оператору,
локальные счётчики непрочитанного и аккаунт «Поток» в этот пилот не входят.

## Проверки 06.10.2026

`tests/test_wazzup_pilot.py` — ограничения доступа, защита повторов, таймаут,
конкурентные отправки, изоляция чтения, восстановление истории и ограничения SSE.
`tests/test_wazzup_pilot_persistence.py` выполняет настоящие SQL на отдельном
локальном PostgreSQL (`WAZZUP_PILOT_TEST_PORT`), включая конкурентные статусы/эхо.
Не запускает приложение и не подключается к production.

`tests/wazzup_chat_pilot.test.mjs` и `tests/wazzup_pilot_realtime.test.mjs` проверяют
черновики, двойной клик, неопределённую отправку, объединение событий,
закрытие/восстановление потоков, watchdog и задержку повторов при ошибке базы.
Итого прошли 123 Python-теста (включая 12 на локальном PostgreSQL),
44 JavaScript-теста и production-сборка Vite. Визуальная проверка в браузере
и отправка реальному получателю не выполнялись.

Локальный транспортный benchmark:

```powershell
python scripts/benchmark_wazzup_pilot.py --clients 6 --events 300 --rate 30 --background-streams 24
```

Waitress 96 потоков, 6 SSE пилота плюс 24 фоновых потока: 1800/1800 доставок,
publish→SSE p95 3.98 мс, максимум 10.09 мс. Обычный HTTP GET p95 6.43 мс,
ошибок и утечек слотов нет. Это локальный транспорт, без Wazzup, PostgreSQL,
прокси, браузерного обновления и production-авторизации.

Малый read-only замер текущей БД (`scripts/benchmark_wazzup_pilot_db.py --run`):
6 имитированных клиентов, 3 цикла, 72 SELECT через 2 соединения служебной роли.
У этой роли лимит 2; это не пул приложения (по умолчанию 16–40).
С учётом сети от рабочей станции p95: COUNT чатов 98.65 мс, список 112.11 мс,
сообщения LIMIT 50 — 92.82 мс, LIMIT 200 — 195.46 мс.
Выбранный чат содержал лишь 17 сообщений: этот тест не характеризует длинные
переписки. Очередь на два соединения достигала 3.83 с, цикл с очередью — 4.45 с.
Она не является измерением задержки рабочего интерфейса.

Результаты подтверждают работоспособность транспорта для 6 подключений.
Полную задержку Wazzup→вебхук→браузер, длинные истории и одновременную нагрузку
остальных разделов следует измерять на сервере после выкладки. Общие лимиты
SSE колокола/аукциона и пилота пока независимы; перед массовым включением
следует проверить суммарное число занятых потоков Waitress.

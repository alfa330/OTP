# Мост «Касания» — CDR АТС → портал

Служба, которая живёт **внутри корпоративной сети** и приносит порталу звонки
отдела продаж. Половина раздела «Касания»; вторая половина — `cdr/` на портале.

## Зачем он нужен

Станция FreePBX (`192.168.17.44`) стоит в корпоративной сети. 25.08.2026 её
вывели наружу через прокси с basic-auth — в тот же день сервис лёг, и внешний
доступ закрыли. Портал живёт на Render и до сети не дотягивается.

Поэтому ходит тот, кто внутри. Мост делает **только исходящие** запросы к
порталу: наружу не открывается ни одного порта, во входящем файрволе ничего
менять не надо, а то, что закрыли, не приходится открывать заново.

```
   портал (Render)                     корпоративная сеть
┌────────────────────┐            ┌──────────────────────────────┐
│  раздел «Касания»  │            │  VM с этим мостом            │
│  cdr_sync_days     │◄───────────┤  1. что нужно? (poll)        │
│    очередь суток   │   HTTPS,   │  2. читает 192.168.17.44:8000│
│  cdr_touches       │   токен    │  3. склеивает касания        │
│    данные          │◄───────────┤  4. отдаёт результат (day)   │
└────────────────────┘            └──────────────────────────────┘
```

Через интернет едут **3,4 тысячи касаний в сутки вместо 23 тысяч сырых строк
CDR** — склейка делается здесь же, на месте.

## Что он НИКОГДА не делает

**Не трогает ручки станции, которые работают с живым Asterisk.** У станции 24
ручки; `/freepbx/load/queues`, `/freepbx/load/agents` и `/agents/stream` ходят в
AMI. 25.08.2026 три вызова первых двух зависли без ответа, и в течение минут
станция перестала отвечать целиком.

В `station.py` жёсткий белый список из четырёх адресов, и позвать что-то вне его
— ошибка в коде, а не запрос в сеть:

```python
ALLOWED_PATHS = ('/freepbx/cdr', '/freepbx/cdr/count', '/agents/map', '/health')
```

Плюс: одновременных запросов не больше одного, пауза 0,4 с между страницами,
повтор только на обрыв уже установленного соединения (таймаут не повторяется —
станция и так не справляется).

## Установка на Windows-VM

Нужен Python 3.11 и сетевой доступ к станции и к интернету.

### 1. Положить код

```
git clone <репозиторий> C:\otp
cd C:\otp
pip install -r cdr_bridge\requirements.txt
```

Мост берёт склейку из `cdr/touches.py` того же репозитория — своей копии этой
логики у него нет намеренно: она сверена с эталонной выгрузкой построчно, и
разошедшиеся копии обнаружились бы не сразу, а на цифрах в отчёте. Обновление
моста — это `git pull`.

### 2. Задать переменные окружения

Системные (`Панель управления → Система → Переменные среды`), чтобы их видела
служба, а не только ваша консоль:

| Переменная | Значение | Обязательна |
|---|---|---|
| `CDR_BRIDGE_PORTAL` | адрес портала, например `https://otp.example.kz` | да |
| `CDR_AGENT_TOKEN` | тот же токен, что задан на портале | да |
| `CDR_STATION_URL` | `http://192.168.17.44:8000` | нет, это значение по умолчанию |
| `CDR_STATION_LOGIN` | логин станции | нет, только если она закроет чтение CDR |
| `CDR_STATION_PASSWORD` | пароль станции | нет |

Токен — **только ASCII**. HTTP-заголовок ходит в latin-1, и токен с кириллицей
не отправится вовсе; портал на такой ответит 401. Сгенерировать:

```
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

Тот же токен нужно прописать на портале (Render → переменные окружения →
`CDR_AGENT_TOKEN`). Мост и портал сверяют его `compare_digest`.

### 3. Проверить связь

**Из каталога репозитория** — `python -m …` ищет пакет в текущем каталоге, и из
`C:\Windows\System32` команда падает с `ModuleNotFoundError: No module named
'cdr_bridge'`:

```
cd C:\otp
python -m cdr_bridge.agent --check
```

Ожидаемый ответ:

```
станция  http://192.168.17.44:8000 — отвечает
портал   https://otp.example.kz — принял, заданий в очереди: 0
```

Затем один проход вручную:

```
python -m cdr_bridge.agent --once
```

### 4. Поставить службой

Через встроенный планировщик (проще всего, перезапускается сам). У `schtasks`
нет ключа «рабочий каталог», а он обязателен — поэтому запускаем через `cmd /c`
со сменой каталога, иначе задача молча падает на `ModuleNotFoundError`:

```
schtasks /create /tn "OTP CDR Bridge" /sc onstart /ru SYSTEM /rl HIGHEST /f ^
  /tr "cmd /c cd /d C:\otp && C:\Python311\python.exe -m cdr_bridge.agent >> C:\otp\logs\cdr_bridge.log 2>&1"
schtasks /run /tn "OTP CDR Bridge"
```

Каталог для логов создать заранее: `mkdir C:\otp\logs`.

Задача должна быть настроена на перезапуск при сбое: `Свойства → Параметры →
Перезапускать при сбое каждые 5 минут`. Проверить, что она действительно
работает: `schtasks /query /tn "OTP CDR Bridge" /v /fo list`.

Либо через NSSM, если он уже используется на машине:

```
nssm install OtpCdrBridge C:\Python311\python.exe -m cdr_bridge.agent
nssm set OtpCdrBridge AppDirectory C:\otp
nssm start OtpCdrBridge
```

## Как он работает

Раз в минуту (а пока есть работа — сразу же) спрашивает портал: какие сутки
нужны. Получив задание, читает CDR за эти сутки **с часовым хвостом следующих**,
склеивает строки в касания и отправляет результат.

**Зачем хвост.** Звонок, начавшийся в 23:59 и закончившийся в 00:03, попадает
плечами в двое суток. Без хвоста он распался бы на два обрубка с неверной
длительностью. Границы окна считает портал, а не мост: правило «сутки плюс час»
— часть логики раздела, и разъехаться двум его копиям негде.

Состояния он не хранит: очередь живёт на портале. Перезапуск моста, VM или
портала не теряет ничего — незакрытое задание вернётся в очередь через 15 минут.

Замеры на живых данных (25.08.2026): сутки отдела продаж — 23 574 строки CDR,
пять страниц по 5000, около 10 секунд чтения; на выходе 3 396 касаний, тело
запроса к порталу 1,3 МБ.

## Диагностика

| Симптом | Где смотреть |
|---|---|
| В разделе плашка «мост молчит» | жива ли задача/служба на VM; логи ниже |
| `Портал не принял токен` | `CDR_AGENT_TOKEN` на VM и на Render различаются |
| `Портал не настроен` (503) | на Render не задан `CDR_AGENT_TOKEN` |
| `станция — НЕ отвечает` | `curl http://192.168.17.44:8000/health` с самой VM |
| Сутки висят в «ошибка» | текст ошибки виден в разделе, у каждой даты свой |

Логи — стандартный вывод; команда планировщика выше уже перенаправляет их в
`C:\otp\logs\cdr_bridge.log`.

Ключи: `--check` (проверка связи), `--once` (один проход), `--verbose`.

## Чего здесь нет

* **Записей разговоров.** Они лежат на `192.168.88.251` и наружу не выведены;
  ссылки в выгрузке открываются только из внутренней сети. Мост эту машину
  видит, так что при необходимости это решаемо — но отдельной задачей.
* **Автообновления.** В отличие от `oktell_recall_guard`, мост ставится на одну
  управляемую VM, а не на парк машин сотрудников: обновление — `git pull` и
  перезапуск службы.
* **Своего exe.** По той же причине: собирать инсталлятор ради одной VM незачем.

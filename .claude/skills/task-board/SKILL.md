# Бэклог и канбан задач OTP

Раздел «Задачи» на фронте — `src/components/tasks/TasksView.jsx` (вкладка «Обзор») +
`src/components/tasks/TaskBoardWorkspace.jsx` (вкладки «Бэклог», «Доска», «Таймлайн»).
Данные — таблица `tasks` в проде.

## Как подключаться

Через прод-API скриптом `scripts/task_board.py`. Логин/пароль берутся из
`.env.codex.local` (`ADMIN_LOGIN`/`ADMIN_PASSWORD`), транспорт — bearer.
Запускать из `C:/python/OTP-1`, для читаемого вывода Cyrillic — `python -X utf8`.

```bash
python -X utf8 scripts/task_board.py board            # канбан по колонкам
python -X utf8 scripts/task_board.py board --mine     # только мои
python -X utf8 scripts/task_board.py backlog          # бэклог в порядке приоритета
python -X utf8 scripts/task_board.py show 412         # карточка целиком (история, чек-лист, факт. старт)
python -X utf8 scripts/task_board.py recipients       # id исполнителей
```

Любая команда принимает `--json` — отдаёт сырой ответ API, удобно парсить.

## Модель данных (важно понимать до правок)

Новых статусов НЕ вводили. Колонки доски — это существующий жизненный цикл:

| Колонка | Условие |
|---|---|
| Бэклог | `is_backlog = true` (статус при этом `assigned`) |
| К выполнению | `is_backlog = false`, `status = assigned` |
| В работе | `status in (in_progress, returned)` |
| На проверке | `status = completed` |
| Готово | `status = accepted` |

Дополнительные поля `tasks`: `is_backlog`, `backlog_rank` (double, ручной порядок
приоритезации), `estimate_minutes` (оценка), `planned_start_at` (плановый старт),
`started_at` (факт. начало — ставится на первом переходе в `in_progress`).

Ключевое правило: **задача в бэклоге не тревожит исполнителя** — Telegram-уведомление
уходит только когда карточка выносится из бэклога (`promote`).

Колонка **«Готово» — скользящее окно на 7 дней**: принятое раньше уходит в архив колонки
(на доске раскрывается кнопкой, в CLI — флагом `board --archive`). Архив вычисляется из
момента приёмки в `task_status_history`, отдельного поля в БД нет — ничего не «архивируется»
физически, задачи никуда не пропадают и остаются в «Обзоре» и таймлайне.

## Задачи себе и источник задачи

Задачу можно поставить самому себе (`--self`, в UI — кнопка «Себе» рядом с исполнителем):
`created_by == assigned_to`. Кто на самом деле попросил — отдельные поля
`tasks.requested_by_id` (сотрудник) и `tasks.requested_by_name` (свободный текст, если
человека нет в системе). **Оба пустые = своя инициатива** — так и подписано в карточке.
Id имеет приоритет над текстом, чтобы не хранить два ответа на один вопрос.

Это независимо от `created_by`: карточку создал ты, но поручил её кто-то другой.

## Напоминания в Telegram перед дедлайном

Работают и для **заметок** (`task_notes`), и для **задач** (`tasks`): поле
`reminder_minutes_before` — за сколько минут предупредить, `NULL` = выключено.
**Жёсткий предел — 1440 минут (сутки)**, и в CHECK-констрейнте, и в UI, и в CLI:
больше суток напоминание бесполезно. По умолчанию при установке дедлайна
предлагается «за день», значение можно сменить или выключить.

Рассылку гоняет cron `task_deadline_reminders` каждые 5 минут
(`send_due_task_reminders` → `db.collect_due_task_reminders`). Условия отправки:
дедлайн ещё не прошёл, задача/заметка не закрыта, задача не в бэклоге, у адресата
есть `telegram_id`. `reminder_sent_at` ставится **только после успешной отправки**
и сбрасывается, если сдвинули срок или интервал — тогда напомнит заново.

```bash
python -X utf8 scripts/task_board.py create "Тема" --self --in 3d --remind 1d
python -X utf8 scripts/task_board.py deadline 92 --due "2026-08-05 18:00" --remind 3h
python -X utf8 scripts/task_board.py deadline 92 --remind off
```

Форматы `--remind`: `1d`, `3h`, `30m`, `за день`, `off`. Больше суток → явный отказ.

## Отчёты о проделанной работе

Таблица `task_reports`: журнал по задаче. `kind='progress'` — промежуточный отчёт (можно
писать по ходу работы), `kind='completion'` — итоговый (создаётся автоматически при сдаче
задачи через `status ... completed`). `spent_minutes` — фактические трудозатраты;
сумма по отчётам приходит в задаче как `spent_minutes` и сравнивается с `estimate_minutes`
(чип «факт / оценка» на карточках, метрика «Факт к оценке» на таймлайне).

`tasks.completion_summary` НЕ убирали — он денормализованно хранит текст последнего
итогового отчёта (для Telegram, закреплённого виджета и выгрузок). Правишь итоговый
отчёт — синхронизируется автоматически, руками `completion_summary` не трогай.

Права: писать отчёт может исполнитель, постановщик или админ; **править и удалять —
только автор** (админ может удалить чужой, но не переписать). Отчёт при сдаче
обязателен: `status <id> completed` без `--report` CLI отклонит.

## Команды изменения

```bash
# создать
python -X utf8 scripts/task_board.py create "Тема" --assignee 169 --backlog --estimate 4h
python -X utf8 scripts/task_board.py create "Тема" --assignee 169 --due "2026-08-05 18:00" --priority urgent

# себе (своя инициатива) / себе, но поручил кто-то
python -X utf8 scripts/task_board.py create "Тема" --self
python -X utf8 scripts/task_board.py create "Тема" --self --from 169
python -X utf8 scripts/task_board.py create "Тема" --self --from-name "директор на планёрке"

# записать УЖЕ сделанную работу одной командой (создать себе → в работу → сдать отчётом → принять)
python -X utf8 scripts/task_board.py log "Починил выгрузку Oktell" --report "что сделано" --spent 2h30m
python -X utf8 scripts/task_board.py log "Разбор инцидента" --report "итог" --spent 4h \
    --progress "поднял логи, нашёл причину" "починил и проверил на проде" --from 169
python -X utf8 scripts/task_board.py log "Тема" --report "итог" --spent 1h --keep-open   # оставить на проверке

# дедлайн / оценка / плановый старт
python -X utf8 scripts/task_board.py deadline 412 --due "2026-08-05 18:00"
python -X utf8 scripts/task_board.py deadline 412 --in 3d4h --estimate 90
python -X utf8 scripts/task_board.py deadline 412 --clear

# бэклог ↔ доска
python -X utf8 scripts/task_board.py promote 412     # в работу (уведомит исполнителя)
python -X utf8 scripts/task_board.py park 412        # обратно в бэклог (только status=assigned)

# приоритет в бэклоге
python -X utf8 scripts/task_board.py rank 412 --top
python -X utf8 scripts/task_board.py rank 412 --after 408

# статус
python -X utf8 scripts/task_board.py status 412 in_progress --comment "взял"
python -X utf8 scripts/task_board.py status 412 completed --report "что сделано" --spent 3h30m
python -X utf8 scripts/task_board.py status 412 accepted

# отчёты о проделанной работе
python -X utf8 scripts/task_board.py reports 412                                  # журнал
python -X utf8 scripts/task_board.py report 412 "Поднял индексы" --spent 2h       # промежуточный
python -X utf8 scripts/task_board.py report 412 "Готово, вот итог" --spent 1h --final
```

Форматы длительности: `90`, `90m`, `4h`, `3d4h`, `2ч30м`.
Форматы даты: `"2026-08-05 18:00"`, `2026-08-05` (→ 18:00), `05.08.2026 14:30`, ISO.

## Приёмку итога делает поручитель — НЕ исполнитель

Жёсткое правило (владелец указал прямо): **принять итог задачи может тот, кто её поручил.**
Порядок определения приёмщика: `requested_by_id`, если он указан, иначе `created_by`.

- Исполнитель **не принимает свою же работу** — API возвращает 403, кнопки «Принять»
  и «Вернуть» ему не показываются, перенос карточки в «Готово» блокируется.
- Единственное исключение — **своя инициатива** (сам поручил, сам делаешь): принимать
  больше некому, иначе задача навсегда застряла бы на проверке.
- Поручитель поэтому: видит задачу (даже если карточку создал не он), получает
  Telegram-уведомления по ней, а при сдаче — отдельную строку «Задача ждёт вашей приёмки».

**Что это значит для меня:** сдав работу (`status <id> completed`), я **останавливаюсь**.
Не вызываю `accepted` — задача должна остаться в «На проверке». Исключение: задача целиком
своя инициатива без поручителя (тогда `log` закрывает её сам, это его штатное поведение).
Если поручитель указан, а я всё же вызвал `accepted` — это ошибка, надо вернуть задачу
через `reopened` и снова сдать отчётом.

## Права (API их проверяет, не пытайся обойти)

- `in_progress` / `completed` — только исполнитель.
- `accepted` / `returned` / `reopened` — поручитель (или постановщик, если поручителя нет);
  админ и СВ могут принять за него, но не свою собственную работу.
- `due_at` / `planned_start_at` — постановщик или админ.
- `is_backlog` / `backlog_rank` / `estimate_minutes` — постановщик, исполнитель или админ.
- В бэклог возвращается только не начатая задача (иначе 409 `BACKLOG_ONLY_FOR_ASSIGNED`).

## Как ставить «правильный» дедлайн

1. `show <id>` — посмотри `estimate_minutes`, `started_at`, историю и чек-лист.
2. Если оценки нет — сначала поставь её (`deadline <id> --estimate ...`); без оценки
   срок берётся с потолка, и таймлайн ничего не показывает.
3. Дедлайн = плановый старт + оценка + буфер. Учитывай реальный темп: медианный цикл
   команды виден на вкладке «Таймлайн», а `show` даёт факт по конкретной задаче.
4. Ставь абсолютный `--due` (а не `--in`), если срок привязан к дате/событию.
5. Не двигай чужие дедлайны молча — это меняет обязательство, скажи пользователю.

## Прямой API (если нужен нестандартный запрос)

- `GET /api/tasks?backlog=only|exclude&status=&tag=&priority=&limit=&offset=`
- `POST /api/tasks` (multipart) — поля `is_backlog`, `estimate_minutes`, `due_at`, `planned_start_at`
- `PATCH /api/tasks/<id>` (json) — `due_at`, `estimate_minutes`, `planned_start_at` + прежние поля
- `POST /api/tasks/board` (json) — батч планирующих правок:
  `{"items":[{"task_id":412,"is_backlog":false,"backlog_rank":2.5,"estimate_minutes":120,"due_at":"..."}]}`
- `POST /api/tasks/<id>/status` (json) — `{"action":"in_progress","comment":""}`;
  для `completed` — `{"action":"completed","report":"...","spent_minutes":210}`
- `GET|POST /api/tasks/<id>/reports` — журнал отчётов; POST `{"body":"...","spent_minutes":120,"kind":"progress"}`
- `PATCH|DELETE /api/tasks/reports/<report_id>` — правка/удаление своего отчёта

Реализация: роуты в `bot_schedule2.py` (`handle_tasks`, `handle_single_task`,
`handle_tasks_board`, `handle_task_reports`, `handle_task_report_item`,
`update_task_status`), логика — `database.py` (`create_task`, `edit_task`,
`update_task_board_state`, `update_task_status`, `create_task_report`,
`update_task_report`, `delete_task_report`, `get_tasks_for_requester`).

## Что от меня ждут по умолчанию (не спрашивать каждый раз)

Владелец проекта повторяет это почти в каждой задаче — считай требованиями, а не пожеланиями.
Относится к любой работе по проекту, не только к разделу «Задачи».

**Визуальный и информационный шум — главный критерий брака.** Формулировка владельца:
«нельзя чтобы был лишний информационный и визуальный шум, это очень важно». Практически:

- Цвет только там, где он несёт смысл (просрочка, перерасход, готово). Нейтральное состояние
  не красим вообще — например, обычный приоритет на доске не рисуется никак.
- Не дублировать одну и ту же информацию в двух местах на одном экране (итог задачи
  показывается либо в журнале отчётов, либо отдельным блоком — но не оба).
- Не выкладывать все поля формы сразу: на виду обязательное, остальное — кнопками
  (см. `TaskComposerForm`: тема + описание + исполнитель, дальше чипы `+ Дедлайн`, `+ Оценка`…).
- Подсказки и хинты — только когда открыта соответствующая секция, не постоянно.
- Числа — `tabular-nums`, иначе они «прыгают» при обновлении.

**Стиль — macOS/iOS, как на остальном сайте.** Не изобретать: брать примитивы из
`src/components/ui/ios.jsx` (`APPLE_FONT`, `iosCard`, `IosModal`, сегментные контролы),
палитра slate, `rounded-2xl`, `ring-1 ring-slate-200/70`, мягкие тени, `active:scale-[0.98]`.
Полноэкранные режимы — через общий `src/components/common/FullscreenSheet.jsx`.
Если раздел живёт в своей типографике (как `.tv-root` с DM Sans/Syne) — новый блок
оборачивать в свой scope и не смешивать шрифты в одном кадре.

**Оптимизация — обязательна, а не «если успеешь».**

- Не тянуть данные повторно: если список задач уже есть в состоянии, доска/бэклог/таймлайн
  считаются из него мемоизацией, а не отдельными запросами.
- Батч вместо N запросов (`POST /api/tasks/board` принимает массив `items`).
- Оптимистичные правки — только для полей, где ответ сервера совпадёт с локальным значением
  (числа, флаги). Для дат — нельзя: сервер нормализует таймзону, и оверрайд залипнет.
- Тяжёлые списки — не рендерить дважды (полноэкранный режим переиспользует ту же разметку).
- В БД — индексы под новые выборки, миграции идемпотентные (`IF NOT EXISTS`, `NOT EXISTS`
  в бэкфиллах), схему не ломать: предпочитать флаг/новую таблицу расширению `CHECK`-констрейнта.

**Best practice, а не самодеятельность.** По незнакомой предметной области (канбан, бэклог,
оценки, отчётность) сначала сверяться с тем, как это делают продукты и форумы, и переносить
проверенное: один упорядоченный бэклог вместо папок, WIP-лимит на колонке «В работе»,
скользящее окно в «Готово» вместо бесконечного списка, медианы вместо средних в метриках
цикла, оценка отдельно от факта. Если решение спорное — объяснить выбор словами, а не молчать.

**Ещё из практики работы с владельцем:**

- Весь UI-текст по-русски, включая тосты и ошибки.
- Коммит и пуш — прямо в `main`, без ветвей и PR; **без трейлера `Co-Authored-By`**.
- Пуш в `main` = деплой на Render, поэтому перед пушем спрашивать, а после — проверять,
  что деплой `live` и миграции применились (логи + read-only БД).
- После правок фронта прогонять `npm run build`, после правок бэкенда — весь `pytest tests/`.

## Как писать отчёт (когда просят отчитаться за меня)

**Отчёт читает коллега, а не разработчик.** Требование владельца: отчёт должен быть понятен
человеку не из разработки — например тому, кто задачу поручил. Это относится и к новой
функциональности, и к исправлениям.

Пиши от лица пользователя, а не кода:

| Нельзя | Надо |
|---|---|
| «добавил `reminder_minutes_before` в `task_notes` + CHECK ≤ 1440» | «у заметки с дедлайном можно выбрать, за сколько предупредить; больше чем за день поставить нельзя» |
| «cron каждые 5 минут, `collect_due_task_reminders`» | «система сама проверяет сроки и присылает сообщение в Telegram» |
| «`reminder_sent_at` ставится после 200 от Telegram» | «если Telegram был недоступен, сообщение не потеряется — попробует снова» |
| «npm run build успешно, 813 passed» | «проверено на рабочем сервере: настройка сохраняется, рассылка работает» |

Структура, которая работает:
1. **Одна фраза — что теперь можно** («напоминания о дедлайнах приходят в Telegram»).
2. **Как пользоваться** — куда нажать, буквально по шагам с названиями разделов и кнопок.
3. **Что учли** — решения, заметные пользователю (что не тревожим по просроченному,
   что повторов не будет), без внутренней механики.
4. **Что проверено и что нет** — честно, но без тестовой терминологии.

Никаких имён полей, таблиц, функций, файлов, коммитов, названий тестов и команд сборки.
Технические детали, если они правда нужны — в память или в скилл, не в отчёт коллеге.

Дальше по механике:
1. `show <id>` — посмотри чек-лист, историю и уже написанные отчёты, чтобы не дублировать.
2. Текст по делу: что сделано → к какому результату пришли → что осталось/риски.
   Не пересказывай тему задачи и не пиши «выполнено» без содержания.
3. `--spent` ставь только если есть на чём основываться (история статусов, твои же
   замеры). Выдумывать трудозатраты нельзя — они идут в метрики оценок.
4. Промежуточный отчёт (`report`) не меняет статус. Сдача — `status <id> completed --report ...`.
5. Работу, которой ещё нет в системе, записывай командой `log` — она создаст задачу на
   владельца, проведёт через работу и закроет отчётом. Так процесс виден в истории статусов
   и в таймлайне, а не появляется «из ниоткуда» уже закрытым.
6. CLI логинится под владельцем (`ADMIN_LOGIN`), то есть отчёт пишется **от его имени**.
   Поэтому: не выдумывай содержание — если не знаешь, что именно было сделано, спроси.
7. Сдал отчёт — **не принимай задачу**, если есть поручитель (см. раздел о приёмке выше).

# Oktell Recall Guard v1.0

Ограничитель просиживания в статусе «Перезвон» на рабочем месте оператора:
когда накопленное время в «Перезвоне» превышает порог, оператора
**по-настоящему разлогинивает** из веб-клиента Oktell (`https://<веб-клиент Oktell>/`).

## Почему не серверной командой

Серверная команда Oktell `wp_setuserstate?user=<логин>&oncallcenter=0` умеет
только **снять с линии**. Проверено на живом операторе 17.08.2026: статус стал
`Готов`, `IsCC=false`, но оператор **остался залогинен** и вернулся в «Перезвон»
через 75 секунд. Настоящего logout у HTTP-интерфейса Oktell нет.

Настоящий разлогин — действие внутри браузера: стереть сессию
`___oktellsessionid` и перезагрузить страницу, после чего оператор снова вводит
пароль.

## Где считается правило: в самом окне

Клиент Oktell получает от сервера события статуса по своему WebSocket:

```json
["getuserstateresult", {"onlunch": true, "lunchreasonid": 2,
                        "userlogin": "6612", "userstatestr": "usLunch"}]
```

`onlunch: true` + `lunchreasonid: 2` — это и есть «Перезвон» (справочник
подпричин: 1 Тех.причина, 2 Перезвон, 3 Тренинг, 4 Перерыв). Поэтому правило
живёт прямо в странице:

- **ноль опросов базы** — в первой версии правило дёргало `A_UserStateHistory`
  через SQL-прокси, и этот прокси дважды за день отваливался;
- **ноль нагрузки на наш сервер** — решение принимается локально;
- **лаг ~0** вместо 5–15 секунд;
- видно то, чего база не видит в принципе (реальное бездействие в интерфейсе —
  задел на будущее).

Цена решения: судья находится на машине оператора, то есть снимается вместе с
агентом. Это закрывается сверкой по **уже приходящему** снимку табло СЗоВ
(он и так тянет статусы всех операторов раз в ~13 с) — новых запросов ноль.
Эта сверка ещё не сделана, см. «Что не сделано».

## Как считается время

| Событие | Что происходит со счётчиком |
|---|---|
| Вошёл в «Перезвон» | пошёл отсчёт |
| Переключился на «Готов» и обратно | **накопленное сохраняется** — иначе ограничитель обходится в один клик |
| Перезагрузил страницу (F5) | **накопленное сохраняется** (лежит в `localStorage`, ключ по логину и дню) |
| Состоялся звонок | **счётчик обнуляется** — это единственное, что его обнуляет |
| Новый день | счётчик начинается заново |
| Порог − 30 с | плашка поверх клиента с обратным отсчётом |
| Порог | штатный `["logout",{}]` в сокет, снос сессии, перезагрузка → экран входа |

Настройки — раздел `in_window_rule` в конфиге:

```json
"in_window_rule": {
  "enabled": true,
  "threshold_s": 180,
  "warn_before_s": 30,
  "recall_lunch_reason_id": 2,
  "call_state_strings": ["talk", "dial", "call", "ring"],
  "call_state_ids": [],
  "message": "«Перезвон» дольше 3 минут — сессия будет закрыта"
}
```

⚠️ `call_state_strings` — **пока догадка**. Достоверно наблюдались состояния
`usLunch`, `usReady`, `usWOphone`; как называется состояние разговора, надо
подтвердить одним живым звонком. Правило запоминает встреченные состояния в
`window.__oktellGuardRule.seenStates` — оттуда и берётся точное имя.

Правило несёт версию-отпечаток (`ruleVersion`): если в открытой вкладке
работает правило от старого exe, агент один раз перезагружает страницу.
Без этого обновлённый порог доезжал бы до оператора только после того, как он
сам перезагрузит вкладку.

## Роль exe

Один файл `OktellRecallGuard.exe` в четырёх режимах:

```text
OktellRecallGuard.exe              -> первый запуск: поставить себя; потом watchdog
OktellRecallGuard.exe --agent      -> открывает окно Oktell, ставит правило, шлёт heartbeat
OktellRecallGuard.exe --open       -> открыть управляемое окно Oktell (ярлык сотрудника)
OktellRecallGuard.exe --install    -> установка явной командой
OktellRecallGuard.exe --uninstall  -> снять автозапуск, задачу и ярлык
OktellRecallGuard.exe --logout-now -> разлогинить прямо сейчас (ручная проверка)
OktellRecallGuard.exe --status     -> состояние в JSON (+ status.json рядом с логами)
```

Агент **не считает время** — он открывает управляемое окно, устанавливает в него
правило, следит, что окно живо, и отчитывается о состоянии. Управляемое окно —
это Chrome со **своим профилем** и портом отладки CDP **на loopback**:

```text
chrome.exe --user-data-dir=%LOCALAPPDATA%\OktellRecallGuard\chrome-profile
           --remote-debugging-port=0 --remote-debugging-address=127.0.0.1
           --ignore-certificate-errors-spki-list=<отпечаток сертификата Oktell>
           --app=https://<веб-клиент Oktell>/
```

Свой профиль обязателен: Chrome блокирует remote-debug на профиле по умолчанию.
Порт слушает только `127.0.0.1`.

**Сертификат Oktell самоподписанный** (выписан внутренним удостоверяющим
центром). На чистом профиле Chrome показывает «Подключение не защищено» и сам
это не проходит. Поэтому в аргументах — точечный пин отпечатка того самого
сертификата, без глобального отключения проверок. Правильный путь для боевой
раскатки — положить внутренний корневой сертификат в доверенные корневые
(пользователю это доступно без прав администратора), тогда флаг не нужен.

## Как это получает сотрудник

Один файл, никаких зависимостей и никаких .bat:

1. сотрудник скачивает `OktellRecallGuard.exe` с iCORE;
2. запускает двойным кликом — **exe ставит себя сам**;
3. дальше ничего не делает: настройки приезжают с сервера.

Что делает exe при первом запуске (всё без прав администратора):

- копирует себя в `%LOCALAPPDATA%\OktellRecallGuard`;
- прописывает автозапуск в `HKCU\...\Run` (задача с триггером ONLOGON
  требует админа, поэтому именно Run);
- кладёт на рабочий стол ярлык `Oktell` → `exe --open`;
- запускает себя и забирает настройки с сервера.

Снять всё: `OktellRecallGuard.exe --uninstall`.

**Пока сервер не отдал настройки, агент ничего не открывает** — пишет ошибку в
лог и ждёт. Без этого свежескачанный exe открывал сотруднику окно на
несуществующий адрес.

Браузер: сначала ищется Chrome, если его нет — Edge (он тоже Chromium и есть на
любой Windows). Это единственная внешняя зависимость, и она закрыта.

### Выпуск версии

Право выложить версию = право заменить программу на всех машинах операторов,
поэтому вокруг него собрано больше проверок, чем вокруг остального:

* ключ отдельный (`OKTELL_GUARD_PUBLISH_TOKEN`) и в exe не попадает никогда —
  агентский лежит внутри скачиваемого файла и для такого права не годится;
* слабый ключ **выключает публикацию совсем** (нужно от 24 символов, латиница
  вперемешку с цифрами): «почти защищённо» здесь означает незащищённо;
* сравнение постоянного времени — обычное `==` отвечает тем быстрее, чем раньше
  расходятся строки, и по этой разнице ключ подбирают посимвольно;
* пять неудачных попыток с адреса блокируют его на 15 минут;
* принимается только Windows-программа (сигнатура `MZ`) правдоподобного размера
  и номер версии строго вида `1.2.3`;
* отпечаток присылается заранее и сверяется с посчитанным на сервере — файл,
  доехавший не таким, каким его собрали, не публикуется;
* сам ключ в лог не пишется никогда, пишутся только факт, адрес и отпечаток.

Руками никто ничего не загружает: `build_exe.bat` после сборки вызывает
`publish_release.py`, тот кладёт файл в хранилище и делает версию текущей, а
агенты подхватывают её автообновлением. Номер версии берётся из `agent.py`:
второй источник номера однажды разошёлся бы, и агенты либо обновлялись бы по
кругу, либо не увидели бы новую версию. Нужны `OKTELL_GUARD_PUBLISH_TOKEN` и
`OKTELL_GUARD_SERVER`; без них шаг пропускается, exe просто остаётся локально.

### Автообновление

Сотрудник скачивает файл один раз, поэтому новые версии агент ставит сам:

1. раз в 6 часов (и при старте) читает `GET /api/oktell_guard/version` →
   `{"version": "1.1.0", "url": "...", "sha256": "..."}`;
2. если версия **строго выше** своей — качает файл и сверяет `sha256`;
   не совпал — файл удаляется, обновления нет;
3. работающий exe переименовывается в `*.old.exe` (Windows это позволяет),
   новый встаёт на его место, запускается и завершает старый;
4. хвост `*.old.exe` подчищается при следующем старте.

Обновление только вверх: опечатка в манифесте не должна откатывать всем
машинам рабочую версию. Без `sha256` в манифесте обновление не ставится.

### Что должно быть на сервере

| Что | Зачем | Статус |
|---|---|---|
| `GET /api/oktell_guard/config` | адрес Oktell, порог, пин сертификата | клиент готов, эндпоинта нет |
| `GET /api/oktell_guard/version` + раздача файла | автообновление | сделано |
| кнопка «Скачать» в iCORE (с личным токеном) | сотруднику надо откуда-то взять exe | сделано |
| `POST /api/oktell_guard/heartbeat`, `/violations` | живость агента и факты нарушений | сделано |

**Личный токен.** При скачивании из раздела сервер выдаёт сотруднику личный
токен и отдаёт файл под именем `OktellRecallGuard.<токен>.exe`. Агент читает
токен из собственного имени при первом запуске и сохраняет рядом с логами —
установка переименовывает файл, и иначе токен потерялся бы. Смысл: присланное
подписано конкретным человеком, попытка приписать нарушение коллеге отклоняется
вместе с именем автора, а токен можно отозвать. У сервера только отпечаток.

**Общий токен агента.** Ручки агента закрыты общим токеном (`OKTELL_GUARD_AGENT_TOKEN`
на сервере, он же вшивается в exe при сборке — у сотрудника нет ни конфига, ни
возможности что-то вводить). Настоящим секретом он не является: файл скачивает
любой сотрудник. Его работа — отсекать посторонние запросы из интернета, потому
что эти ручки пишут в нашу базу.

`/version` намеренно оставлена открытой: закрой её — и смена токена станет
ловушкой, агенты со старым токеном не узнают о новой версии и застрянут
навсегда. Смена токена: поменять переменную, пересобрать, загрузить версию —
дальше автообновление разнесёт её само.
| раздел «Настройки» + отчёт по выбросам | порог на сотрудника, общая ссылка, статистика | не сделано |

Частота heartbeat — **раз в минуту**. Раньше стояло 5 секунд (в тестовом
конфиге 3): это наследие схемы, где сервер раздавал команды, и за смену
набегали тысячи пустых запросов. Решение принимает правило в окне, поэтому
агенту достаточно отмечаться и отдавать нарушения.

Ответ `/config` накладывается только на общие ключи (`oktell_url`,
`in_window_rule`, `browser.extra_args`, `poll_interval_s`, `dry_run`,
`unmanaged`); пути, логи и токен машины сервер не переопределяет. Ответ
кэшируется — агент переживает недоступность сервера.

## Сборка (для нас, не для сотрудника)

```bat
build_exe.bat                :: dist\OktellRecallGuard.exe
build_exe_console_debug.bat  :: та же сборка с консолью, для отладки
```

Образец конфига — `config.example.json` (нужен только разработчику: на машине
сотрудника конфига нет, настройки приходят с сервера). Ключи:

| Ключ | Смысл |
|---|---|
| `oktell_url` | адрес веб-клиента, он же origin для CDP |
| `in_window_rule` | само правило (см. выше) |
| `server_url`, `agent_token` | куда отчитываться (heartbeat и факты нарушений) |
| `browser.keep_open` | возвращать окно Oktell, если оператор его закрыл (по умолчанию НЕТ: закрыл — значит закрыл) |
| `browser.extra_args` | сюда кладётся пин сертификата |
| `dry_run` | команды разлогина только логируются — режим обкатки |

## Что видит и чего не видит агент

Наружу уходят: имя машины, пользователь Windows, версия, факт наличия сессии
Oktell, признак экрана входа, URL вкладки и логин оператора (он лежит в
открытой cookie `__oktelllogin` — это логин, не токен).

**Ключ сессии `___oktellsessionid` никуда не передаётся** — он используется
только внутри страницы, чтобы её же и разлогинить. Кадры WebSocket с
разговорами, номерами и данными клиентов не копятся: перехват фильтрует только
кадры со статусом и обрезает их до 800 символов.

## Fail-closed: чем закрывается обход

| Обход | Что происходит |
|---|---|
| Переключил статус туда-обратно | накопленное не сбрасывается |
| Нажал F5 | накопленное не сбрасывается |
| Закрыл окно Oktell | `managed_window: false` в heartbeat; окно НЕ навязывается — открыть заново человек может ярлыком |
| Открыл Oktell в своём Chrome мимо ярлыка | заголовки чужих окон уезжают в `unmanaged_windows` |
| Убил процесс агента | вторая копия (watchdog) поднимает за ~2 с |
| Убил обе копии | программа НЕ воскресает по расписанию: это ничего не давало (в своём браузере ей нечего контролировать), зато шумело. Ловится сервером: агента нет, а Oktell показывает человека в «Перезвоне» |
| Снёс автозапуск | heartbeat пропадает — это само по себе нарушение (сверка по табло, не сделана) |

Честно: exe без GPO/Intune снимается пользователем с правами локального
администратора — ровно как в `microsip_dnd_shield`. Гарантия не в exe, а в
серверной сверке.

## Демо и стенд

```bat
dev_harness\demo_live.bat   :: поднять всё и открыть настоящий Oktell
dev_harness\demo_stop.bat   :: остановить
```

`demo_live.bat` требует `dev_harness\config.real.json` — он не в git (в нём
внутренний адрес и пин сертификата). Собрать его можно из `config.example.json`:
`oktell_url` = адрес веб-клиента, `browser.extra_args` = пин сертификата,
`server_url` = `http://127.0.0.1:8799` (локальный приёмник).

`dev_harness\mock_server.py` — заглушка серверной стороны: принимает heartbeat и
ack, отдаёт команды из очереди (`/queue?type=logout`), плюс фальшивая страница
клиента для проверок без прода. Команды нужны для второй, серверной ветки
исполнения — она осталась в агенте как запасной путь.

## Грабли, на которые уже наступили

1. **`Page.addScriptToEvaluateOnNewDocument` без `Page.enable` не работает.**
   Возвращает identifier, но в новый документ скрипт не попадает.
   `Page.disable` звать нельзя: он очищает список добавленных скриптов.
2. **CDP-подключение должно быть постоянным.** При отключении клиента Chrome
   снимает его скрипты: при переподключении на каждый опрос хук не доживал до
   следующей загрузки страницы.
3. **Chrome помнит состояние окна в профиле.** Окно открывалось свёрнутым
   (координаты `-32000,-32000`), и демо выглядело как «Chrome не запустился».
   Агент разворачивает окно сам; при `warn` — без кражи фокуса, при `logout` —
   с подъёмом поверх. Скриншот через CDP на свёрнутом окне зависает.
4. **Гонка при старте:** порт отладки отвечает раньше, чем появляется вкладка,
   поэтому разворачивать окно сразу после запуска нечего — нужно дождаться цели.
5. **Битый config.json нельзя молча подменять дефолтами** — агент уходил
   открывать чужой адрес и стучаться на чужой сервер. Теперь он отказывается
   работать и ждёт исправленный файл.
6. **Правило в открытой вкладке не обновляется вместе с exe** — хук идемпотентен.
   Лечится версией-отпечатком и разовой перезагрузкой.
7. **Powershell/`tasklist` показывает две строки на одну копию** — так работает
   PyInstaller onefile (бутлоадер + процесс). Это не два агента.

## Что не сделано

- **подтвердить состояние разговора** одним живым звонком и заменить догадку
  `call_state_strings` точным значением;
- **отправка фактов нарушения на сервер**: запись копится в странице
  (`localStorage.__oktell_guard_violations`), агент её ещё не читает и не шлёт;
- **сверка по снимку табло** (fail-closed для снятого агента);
- решить, обнуляет ли счётчик **входящий** звонок или только исходящий;
- канареечный сигнал «правило не видит статус» — иначе смена формата события
  вендором тихо убьёт ограничитель;
- уведомление СВ и раздел с нарушениями.

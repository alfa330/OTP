# Требование к API TEZ APP: дата последнего заказа водителя

Мы считаем работу отдела продаж Tez КЦ автоматически: оператор звонит водителю,
и если водитель после звонка выходит на линию — это «успешка», от неё зависит
выплата оператору. Дату выхода на линию мы берём у вас через
`POST /drivers/first-orders`.

Правило зачёта меняется. Новое правило владельца:

> Успешка засчитывается, если между **последним заказом** водителя и **новым
> заказом** прошло не менее 30 дней и в этом промежутке был наш звонок.

То есть мы платим за **реактивацию уснувшего водителя**, а не только за
привлечение нового. Сегодняшний ответ эндпоинта такое правило посчитать не
позволяет: в нём есть только **первые** заказы месяцев, а нужен **последний**
заказ перед новым.

## 1. Чего не хватает — на примере

Сейчас на водителя приходит:

```json
{
  "phone": "+77012345678",
  "month_first_order_at": "2026-07-05T09:12:03+05:00",
  "previous_month_first_order_at": "2026-06-02T18:40:11+05:00"
}
```

Водитель заказывал 2 и 25 июня, новый заказ — 5 июля. Правильный ответ:
разрыв 10 дней, успешки нет. Но мы видим только первый заказ июня (2-е число) и
вычисляем разрыв 33 дня — то есть заплатим за водителя, который никуда не уходил.
Определить это на нашей стороне нельзя ни одним дополнительным запросом: сколько
месяцев назад мы ни спросим, в ответе всегда **первый** заказ месяца.

## 2. Что просим добавить — одно поле

Аддитивно к текущему ответу `POST /drivers/first-orders`, без изменения
существующих полей (мы читаем их в проде, ломать контракт не нужно):

| поле | тип | смысл |
|---|---|---|
| `last_order_before_at` | ISO 8601 / null | дата последнего **завершённого** заказа водителя строго **до 1-го числа запрошенного месяца**, за всё время (без ограничения окном). `null` — заказов не было вообще |

Больше ничего не нужно: разрыв мы считаем у себя как
`month_first_order_at − last_order_before_at`, а `null` в этом поле однозначно
означает «водитель никогда не работал».

Почему граница — 1-е число месяца, а не сам `month_first_order_at`: между началом
месяца и первым заказом месяца заказов нет по определению, поэтому дата выходит
та же самая, но такая формулировка определена и тогда, когда водитель в этом
месяце ещё не выехал, и не меняется при появлении новой поездки. Значит поле,
как и `month_first_order_at`, можно запросить один раз и закэшировать — лишних
обращений к вам не будет.

Поле `previous_month_first_order_at` при этом становится нам не нужно. Удалять
его не просим (ломать контракт ради нас не стоит) — мы просто перестанем им
пользоваться.

Пример желаемого ответа:

```json
{
  "drivers": [
    {
      "phone": "+77012345678",
      "month_first_order_at": "2026-07-05T09:12:03+05:00",
      "previous_month_first_order_at": "2026-06-02T18:40:11+05:00",
      "last_order_before_at": "2026-06-25T21:05:00+05:00"
    }
  ]
}
```

Формат дат и таймзону сохранить как сейчас: ISO 8601 со смещением `+05:00`,
`null` = данных нет. Лимит 100 водителей на запрос нас устраивает.

## 3. Альтернатива, которая закрывает вопрос навсегда

**Предпочтительный для нас вариант — п.2 выше**, он же, по нашей оценке, самый
дешёвый и для вас: нового эндпоинта не появляется, а `last_order_before_at` —
это один поиск назад по индексу `(водитель, дата завершения)`. Нам это не
добавляет ни одного лишнего запроса.

Варианты ниже — на случай, если менять существующий метод неудобно. Они лучше
тем, что при следующем изменении правил (30 → 45 дней, «две поездки вместо
одной») правки на вашей стороне уже не потребуются.

**(а) Заказы за интервал.**

```
POST {base}/drivers/orders
{
  "from": "2026-04-01",
  "to":   "2026-07-31",
  "drivers": [{"phone": "+77012345678"}]
}
```
→ по каждому телефону список дат завершённых заказов (или агрегат по дням).

**(б) Пара вокруг опорной точки** — точный ответ на наше правило и вообще без
месячной семантики: `ref_at` = время нашего звонка. Оговорка: этот вариант для
нас дороже остальных, потому что спрашивать по нему можно только тех, кому уже
позвонили, и переспрашивать после каждого следующего звонка, а на вопрос «выехал
ли водитель в этом месяце» он не отвечает — `first-orders` всё равно останется.

```
POST {base}/drivers/orders-around
{
  "drivers": [{"phone": "+77012345678", "ref_at": "2026-07-14T11:20:00+05:00"}]
}
```
→ `{"prev_order_at": ..., "next_order_at": ...}` — последний заказ строго до
`ref_at` и первый строго после.

## 4. Вопросы, которые надо зафиксировать в контракте

1. **Что считается заказом?** Мы исходим из того, что только **завершённая**
   поездка. Это важно: одна отменённая поездка в середине простоя обнулит
   разрыв 30 дней и снимет с оператора уже заслуженную успешку.
2. **Игнорируются ли неизвестные поля в запросе?** Нужно, чтобы мы могли
   выкатывать своё изменение без синхронного деплоя с вами.
3. **Есть ли рейт-лимит** у `/drivers/first-orders`? Мы шлём пачки по 100
   номеров с паузой 0,3 с, ночью это до ~140 запросов за прогон. Документированного
   лимита мы не нашли — если он есть, назовите цифру, мы подстроимся.

## 5. Операционное: Cloudflare режет наш сервер

Отдельно от полей. Наш прод (Render, регион Frankfurt) обращается к
`api.tezapp.org` с датацентрового IP, и Cloudflare перед вашим API отдаёт на него
**403** — при том что тот же запрос с тем же токеном и теми же заголовками с
обычного IP проходит в 200. Токен тут не при чём: блок срабатывает на периметре,
до проверки токена.

Просим одно из двух:
- добавить исходящий IP нашего сервиса в вайтлист (IP пришлём отдельно), либо
- сделать WAF-исключение для пути `/drivers/first-orders`.

Без этого новый эндпоинт (или новые поля) упрётся в ту же стену.
